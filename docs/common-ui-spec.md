# MY ARCADE 共通UI仕様書

バージョン：1.0

本書は既存10作品で確立した共通UIを、新作ゲーム開発で再利用するための確定仕様である。作品ごとの状態名・内部構造・操作方式の違いを許容し、各ゲーム固有の例外は要件を満たす範囲で明記する。全作品に同じ機能や内部実装を要求しない。

「実装例」と記した記述は選択肢であり、全10作品への実装済み機能を示すものではない。

## 第1章：目的と基本方針

- 全作品の操作性・視認性・画面遷移を統一する。
- Androidの縦画面を優先する。
- HTML・CSS・Vanilla JavaScriptで構成し、原則として外部ライブラリ・ビルド工程を使用しない。
- 各ゲームのルール・難易度・固有の操作性を維持する。
- 新作ゲームは開発開始時から共通UIを実装する。

## 第2章：PAUSE画面のデザイン

PAUSEパネルの表示要素は次の3つのみとする。

- PAUSED
- RESUME
- HOME

| 項目 | 確定仕様 |
| --- | --- |
| 配置 | ゲーム領域の中央 |
| パネル幅 | 260pxを基準とし、狭い画面では収まるよう調整 |
| 背景オーバーレイ | `rgba(0,0,0,0.7)` |
| パネル背景 | `#0b1429` |
| 枠線 | シアン系ネオン枠 `#65efff` |
| RESUME | シアン系で強調 |
| HOME | 控えめな枠線 |
| ボタン配置 | RESUME、HOMEの順に縦並び |
| タッチ領域 | 各ボタンで最低44×44 CSS px |
| アニメーション | なし。フェード・点滅も使用しない |

説明・SCORE・BEST・RETRY・RESETなどをPAUSEパネルに追加しない。PAUSEボタンはゲーム画面上部に配置する。

## 第3章：PAUSE・RESUMEの共通動作

- PAUSE中はゲーム進行を完全に停止する。プレイヤー・敵・弾・演出・タイマーを進めない。
- 停止前の状態を保持し、RESUMEでカウントダウンなしに即時再開する。
- PAUSE時間はプレイ時間やゲーム記録に加算しない。
- 自動再開は禁止する。復帰後も手動RESUMEまで停止を維持する。
- HOMEは確認なしで `../../index.html` へ遷移する。
- ゲーム開始時のカウントダウンは既存仕様を維持する。RESUME時の動作とは区別する。

## 第4章：ゲーム状態管理

START、COUNTDOWN、PLAYING、RESOLVING、PAUSED、GAME OVER、CLEARなどから、作品ごとに必要な状態を定義する。状態名やすべての状態の採用は強制しない。

- PAUSE可能な進行中の状態を作品ごとに定め、PAUSE直前の状態を保存する。
- 重複PAUSEや自動PAUSE通知で、保存した状態を上書きしない。
- RESUMEでは保存した元の状態を復元する。
- START・RETRYでは古いPAUSE状態を破棄する。
- ゲーム終了後は不必要なPAUSEを発生させない。

実装例：PLAYING中の停止ではPLAYINGへ戻し、消去処理をRESOLVINGとして管理する作品では、その処理中の停止からRESOLVINGへ戻す。全作品にRESOLVINGの追加を求めるものではない。

## 第5章：タイマー・アニメーション制御

- 停止時間をプレイ時間に含めず、RESUME後は保持した残り時間・位置から再開する。
- `requestAnimationFrame` 復帰時の基準時刻・時間差分を適切にリセットし、位置飛びや時間の一括消費を防ぐ。
- Canvasのゲーム状態更新を停止する。
- 移動・カメラ・破片・消去・落下など、作品に存在する演出も停止する。
- 必要に応じてWeb Animations APIの `pause()` / `play()` を使用する。

実装例：経過時間の累積値と再開時刻を分けて管理する、または各演出の残り時間を保持する。時計や描画ループの内部構造は作品に応じて選定する。

## 第6章：入力制御

- PAUSE中はゲーム入力を無効にする。
- PAUSE時に長押し・ドラッグ・スワイプの進行状態を解除し、保持中のPointer Captureを解放する。
- キーボードの保持状態・キーリピートを管理し、停止前から継続する入力を再開後へ持ち越さない。
- マルチタッチを考慮し、指が残った状態で再開しても誤操作を発生させない。
- RESUME操作が移動・発射・設置などのゲーム入力として伝わらないようにする。
- RESUME後は新しい入力のみ受け付ける。停止前の指離しやキーリピートで操作を再発動しない。
- 各作品固有の操作感は維持する。

## 第7章：自動PAUSE

次の状況を自動PAUSEの対象とする。

- アプリ切替
- ブラウザー非表示
- フォーカス喪失
- 画面スリープ
- 画面回転
- ページの一時停止
- 長時間の描画中断

使用イベント・検出方法は作品とブラウザーの対応状況に応じて選定する。イベントが重複しても保存状態を壊さず、自動PAUSE後は手動RESUMEまで停止を維持する。

実装例：`visibilitychange`、`blur`、`pagehide` / `pageshow`、`freeze` / `resume`、画面方向の変更通知、描画時刻の間隔監視を組み合わせる。復帰通知は自動再開の指示として扱わない。長時間中断の判定値は作品ごとに定める。

## 第8章：画面回転・レスポンシブ対応

- Android縦画面を優先する。
- タッチ端末の横画面ではRESUMEを禁止する。
- 縦画面復帰後は手動で再開できるようにし、回転だけで自動再開しない。
- セーフエリアを考慮する。
- パネル・ボタンのはみ出し、HUDとの重なり、不自然なスクロールを防ぐ。

確認サイズは320×568、360×640、390×844、430×932、およびPCとする。寸法はCSS pxで扱い、Android実機ではブラウザーのアドレスバーを含む表示領域も確認する。

## 第9章：START・RETRY・終了画面

- STARTでゲームを開始する。
- GAME OVER・CLEARの終了画面にはRETRYとHOMEを用意する。CLEARがない作品に新しい終了条件を追加する必要はない。
- RETRYでは古い入力・PAUSE状態を破棄して再開始する。
- 終了画面とPAUSE画面は別々に管理する。
- 既存のクリア・終了条件を維持する。

## 第10章：記録・設定の保護

- SCORE・BESTの計算を維持する。
- 既存のlocalStorage保存キーを維持する。
- 既存のSOUND設定を維持する。
- 難易度・ゲームバランスを変更しない。
- PAUSE中の不必要な記録更新を防止する。

記録や設定の項目は各作品に存在するものを対象とし、全作品に新しい項目を追加する要件とはしない。

## 第11章：新作ゲームの標準テスト

### 自動テスト

- 状態遷移：開始・停止・元の状態への復帰・重複通知・再試行・終了時のガード。
- UI表示：PAUSEの3要素、配色、配置、タッチ領域、表示収まり。
- ゲーム停止・再開：ゲーム状態と演出を保持し、即時再開できること。
- 時間計算：停止時間を除外し、再開時に位置や残り時間が飛ばないこと。
- 残留入力解除：長押し・Pointer Capture・キーリピート・複数の指・RESUMEによる誤操作。
- 自動PAUSE：非表示・フォーカス喪失・ページ停止・描画中断などと、手動再開までの停止維持。
- 回転対応：横画面の再開制限、縦画面復帰後の手動再開、各確認サイズ。
- 記録保存：BESTなどの保存・再読込・既存設定の維持。
- 既存作品の回帰テスト：新作追加や変更が既存作品を壊さないこと。

### Android実機テスト

- 起動・START。
- PAUSE・RESUME・HOME。
- 停止中のゲーム状態保持。
- タッチ・長押し・誤操作。
- アプリ切替・スリープ・回転。
- 横画面制限と縦画面復帰後の手動再開。
- GAME OVER・CLEAR・RETRY（作品に存在する終了状態を確認）。
- BEST保存。
- 画面収まり。

ゲーム固有のルール・操作・演出・終了条件に必要な追加テストも実施する。存在しない機能のテストは不要とし、該当する機能と例外をテスト結果に記載する。

## 第12章：GitHub・Codex開発運用

- 最新mainから開発ブランチを作成する。
- 原則として1作品につき1PRとする。
- 変更対象を限定し、関係のない作品やファイルを変更しない。
- mainへの直接pushは禁止する。
- 自動マージは禁止し、ユーザーが手動でマージする。
- Android実機確認後に完成判定を行う。

本仕様書の追加は文書のみの独立したPRとする。既存ゲームコード・テスト・README・トップページ・依存関係を変更しない。今回の文書追加では全ゲームのテスト再実行は原則不要とする。

## 第13章：完成判定基準

ゲーム開発・共通UI実装の完成には、次のすべてを満たすことを求める。

- 共通UI仕様への適合（作品固有の例外は理由とともに明記）。
- 自動テスト成功。
- Android実機での動作確認。
- ゲーム固有機能の正常動作。
- 重大な未解決不具合なし。
- ユーザーによる手動マージを経てmainへの反映完了。

PR作成だけでゲーム開発の完成とはしない。今回の作業は仕様書追加のコミット・push・PR作成までを対象とし、マージはユーザーが行う。
